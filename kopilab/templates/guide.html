1 · DARI KLIK KE HASIL

Bagaimana sebuah halaman dibuka?

Bayangkan browser seperti pelanggan yang mengirim pesanan ke dapur. Browser meminta alamat, Flask memilih fungsi yang menangani alamat itu, fungsi membaca atau mengubah data SQLite, lalu Jinja menyusun halaman HTML untuk dikirim kembali.

  1. Browser mengirim request. Contoh: membuka halaman depan atau mengirim form login.
  2. Flask mencocokkan URL. Route di dalam blueprint menentukan fungsi yang dijalankan.
  3. Fungsi memeriksa input dan sesi. Sesi menyimpan konteks browser seperti akun yang sedang masuk dan pilihan mode.
  4. Database membaca atau menyimpan data. Contohnya daftar produk, pesanan, atau progres lab.
  5. Template Jinja membuat tampilan. HTML memakai data yang diberikan route dan mewarisi kerangka `base.html`.
  6. Browser menerima respons. Respons bisa berupa halaman, JSON untuk API, redirect, atau file.
Coba sendiri: buka toko, lalu pencet halaman produk. Pada Request Inspector, perhatikan method, alamat, SQL terakhir, dan header respons. Setiap klik biasanya menghasilkan request baru.

Cara menelusuri satu fitur di source code

  1. Mulai dari tabel route atau URL yang terlihat di browser.
  2. Cari route tersebut di file blueprint yang sesuai, misalnya pencarian berada di `kopilab/blueprints/shop.py`.
  3. Ikuti pemanggilan helper di `kopilab/vulns/` untuk melihat bagian latihan yang berbeda antara mode.
  4. Lihat `kopilab/templates/` untuk memahami bagaimana hasil route ditampilkan.
  5. Cari tes bernama mirip di `tests/` untuk melihat input uji dan hasil yang diharapkan.

3 · SQLITE DAN DATA

Apa yang disimpan di database?

SQLite adalah file database lokal. Ketika aplikasi pertama kali berjalan, KopiLab membuat tabel dan mengisi data contoh. Tidak perlu memasang server database tambahan.

Bedakan data sesi dan data database: sesi browser mengenali pemain, mode, keranjang, dan hint yang sedang dibuka. Progres yang tahan setelah halaman berpindah disimpan di tabel SQLite `lab_solves`, bukan hanya di cookie.

Tombol “Reset progres saya” menghapus progres pemain ini saja. “Reset database lokal” mengembalikan data seed dan menghapus progres semua pemain dalam database lokal—pakai hanya jika memang ingin mulai ulang.

4 · VULNERABLE VS SECURE

Satu alamat, dua pelajaran

Pilihan mode ada di header dan disimpan dalam sesi browser. URL lab tidak berubah. Route yang sama membaca pilihan mode dan memilih perilaku latihan atau pemeriksaan aman.

Vulnerable

Perhatikan kesalahannya

Untuk lab, server sengaja melakukan satu hal yang salah agar dampaknya bisa diamati—misalnya memakai harga dari form browser.

Secure

Ulangi setelah diperbaiki

Handler yang sama memeriksa data dari sumber tepercaya. Contohnya mengambil harga katalog dari database, bukan mempercayai nilai kiriman browser.

Belajar yang disarankan: catat hasil Vulnerable, ganti mode, kirim request yang sama, lalu jelaskan perubahan apa yang membuat server menolak bug tersebut. Ini aplikasi belajar lokal, bukan contoh konfigurasi produksi siap pakai.

5 · SIMULASI TOKO

Alur belanja sebagai contoh aplikasi nyata

  1. Katalog dan pencarian: halaman depan mengambil daftar produk dari SQLite. Pencarian mengirim kata kunci melalui query string.
  2. Detail dan ulasan: route produk mengambil satu produk serta ulasan dan rating yang terkait.
  3. Keranjang: beberapa produk dan jumlahnya disimpan di sesi browser supaya mudah dibawa antarhalaman.
  4. Checkout keranjang: alur toko biasa menghitung ulang harga dari katalog server dan membuat order.
  5. Checkout lab lama: `/checkout` sengaja tetap ada agar flag lama dan pelajaran manipulasi harga tetap berfungsi.
  6. Akun dan akses: login, profil, transfer, riwayat, wishlist, dan panel admin punya route masing-masing.

6 · CARA BELAJAR DI TIAP LAB

Urutan yang membantu saat buntu

  1. Baca tujuan dan endpoint target. Cari tahu halaman atau request yang sedang diuji.
  2. Lakukan langkah praktikum lokal. Ubah satu nilai dalam satu waktu agar sebab dan hasilnya mudah terlihat.
  3. Bandingkan respons atau data. Gunakan Inspector bila perlu.
  4. Buka Petunjuk 1. Kalau masih buntu, lanjutkan Petunjuk 2 dan 3.
  5. Tidak apa-apa membuka solusi kapan saja. Baca jawaban, akar masalah, dan perbaikannya.
  6. Kirim flag untuk menyimpan progres; ulangi request dalam Secure dan jelaskan kenapa hasilnya berubah.

Flag adalah tanda bahwa kamu berhasil mencapai kondisi latihan. Flag bukan password atau data pengguna. Sebagian lab menampilkannya di respons halaman, JSON, atau header `X-Lab-Flag` sesuai contoh.

Progres dan laporan

Submit flag pada kartu lab atau di halaman detail. Server mencocokkan flag, lalu menulis satu baris ke lab_solves; constraint database mencegah satu lab terhitung dua kali untuk pemain yang sama. Halaman /scoreboard merangkum jumlahnya. Tautan laporan pada halaman lab membuat template Markdown berisi ringkasan, severity latihan, langkah reproduksi, dampak, dan rekomendasi.

7 · REQUEST INSPECTOR

Jendela untuk melihat “di balik layar”

Panel Inspector di bawah halaman menyimpan ringkasan request terakhir untuk pemain lokal yang sama.

  • Method dan path: jenis aksi HTTP (misalnya GET untuk membaca, POST untuk mengirim form) dan alamat yang diminta.
  • SQL terakhir: query yang secara eksplisit dicatat oleh route latihan. Pada Secure, nilai input terikat sebagai parameter, bukan ditempel ke sintaks SQL.
  • Header respons: metadata server/browser seperti Content-Type, status, dan cookie. Header dapat berubah berdasarkan mode.

Batasan penting: ini inspector pembelajaran, bukan pencatat semua operasi database. Ia menampilkan query yang dicatat route tertentu; request tanpa query tercatat menampilkan pesan bahwa tidak ada SQL pada request itu.

Urutan melihat data juga penting: panel di respons halaman membaca catatan request sebelumnya, sebab catatan request yang sedang berlangsung baru disimpan saat respons akan dikirim.

8 · BATAS LAB

Kenapa simulator harus tetap lokal?

CSRF simulator berjalan di port 9000 dan service SSRF latihan di port 5001. Keduanya bind hanya ke `127.0.0.1`; SSRF dibatasi ke service internal KopiLab. Upload disimpan di folder proyek dan tidak pernah dijalankan. Simulator tidak membaca cookie, tidak menebak password, dan tidak menghubungi situs pihak lain.

Untuk mencoba simulator CSRF, buka terminal kedua lalu jalankan python run_attacker.py; halaman tetap hanya ditujukan ke `127.0.0.1:5000`. Service SSRF port 5001 mulai bersama aplikasi utama dari `run.py`.

Aturan kelas: lakukan request hanya ke KopiLab di komputer sendiri. Jangan ganti tujuan ke alamat internet, komputer teman, alamat kantor/kampus, atau server publik. Hentikan server dengan Ctrl+C setelah kelas.

10 · CARA MEMASTIKAN SISTEM

Apa yang diperiksa oleh tes otomatis?

  • Tes mode Vulnerable memastikan perilaku lab lama dan tambahan masih bisa diamati pada data lokal.
  • Tes Secure memastikan input serupa ditolak atau diproses dengan aturan lebih aman.
  • Tes toko memeriksa katalog, detail produk, keranjang, checkout, wishlist, dan halaman akun.
  • Tes belajar memeriksa semua halaman materi, hints, solusi, submit flag, scoreboard, reset, Inspector, dan laporan.
Menjalankan tes di Windows:
.venv\Scripts\activate
python -m pytest -q
Tes memakai database sementara. Database toko lokalmu tidak dipakai oleh tes.

Ringkasnya: browser mengirim request → Flask memilih route → handler menjalankan aturan mode → SQLite menyimpan atau membaca data → Jinja menyusun respons. Saat memahami satu route, ikuti urutan ini dan kamu bisa menelusuri hampir semua fitur KopiLab.
